## 第 01 章 项目全景

> 原文档：[docs/01-项目全景.md](../01-项目全景.md)

通过分析约 1,900 个源文件，建立对 Claude Code 架构的全局认知，涵盖技术栈选型、启动链路和模块依赖图。

**核心要点**
- **技术栈**：Bun（运行时 + 打包器，快速启动与编译期 DCE）、TypeScript + Zod（静态 + 运行时类型安全）、forked Ink/React（声明式终端 UI）、Commander.js（CLI 解析）、Yoga 布局引擎。
- **启动链路**：`cli.tsx` → `main.tsx`（4,683 行）→ `init()` → `setup.ts` → `replLauncher.tsx`。
- **模块组织**：`query.ts`（对话循环）、`tools.ts`（工具注册）、`commands.ts`（命令聚合）、`state/`、`services/`、`components/`（380+ 个 UI 文件）、`ink/`（96 文件 forked 框架）。
- **核心数据流**：`用户输入 → query.ts 组装消息 → Anthropic API → 模型返回 tool_use → 工具执行 → 结果反馈 → 模型继续/停止`。
- **关键架构决策**：大型单文件是有意为之的策略集中层；懒加载 `require()` 用于打破循环依赖和编译期 DCE。

**可迁移的设计模式**
1. 分层启动 + 快速路径：每层只加载最少模块，简单命令在最早的层返回。
2. 副作用提升：在 `import` 语句之间插入异步 I/O，与模块求值并行执行。
3. 编译期特性开关 + 条件式 `require()`：配合 `feature()` 实现跨构建变体的零成本代码消除。

## 第 02 章 启动优化

> 原文档：[docs/02-启动优化.md](../02-启动优化.md)

分析让 Claude Code CLI 感觉"瞬间响应"的多层启动优化技术，涵盖快速路径路由、并行 I/O、API 预连接、提前捕获输入、死代码消除和记忆化。

**核心要点**
- **快速路径路由**：`cli.tsx` 在加载完整 UI 栈之前拦截 `--version`/`--help` 和简单非交互式命令。
- **副作用提升**：异步 I/O 调用（读配置、网络预连接）放在 `import` 语句之间，与模块求值并行执行。
- **API 预连接**：启动时就向 Anthropic 端点发起 HTTPS 连接，消除第一次 API 调用的 TCP/TLS 握手延迟。
- **提前捕获输入**：在 Ink UI 完全初始化之前就开始缓冲键盘输入，确保不丢失任何按键。
- **死代码消除（DCE）**：`feature()` 配合 `require()` 使 Bun 打包器在编译时消除未使用代码分支。
- **记忆化**：`memoize()` 缓存昂贵计算（系统提示组装、设置解析），会话内重复调用只付首次代价。

**可迁移的设计模式**
1. 在 import 之间提升异步调用，真正需要时再懒等待结果。
2. 在用户意图明确之前预连接网络，以少量空闲开销换取近零连接延迟。
3. 进程启动时立即缓冲 stdin 事件，UI 就绪后重放。

## 第 03 章 状态管理

> 原文档：[docs/03-状态管理.md](../03-状态管理.md)

介绍 Claude Code 的三层状态管理架构，以及为何一个 35 行的自定义 Store 优于 Redux/Zustand。

**核心要点**
- **三层架构**：① `bootstrap/state.ts`（不可变常量）；② `Store + AppState`（响应式可变会话状态）；③ `ToolUseContext`（每次工具调用的临时上下文，作为函数参数传递）。
- **自定义 Store（约 35 行）**：实现 `useSyncExternalStore` 协议——`getSnapshot()`、`subscribe()`、`setState()`——无外部依赖，无样板代码。
- **`useSyncExternalStore` 集成**：React 18 内置 Hook，保证并发渲染期间读取无撕裂。
- **在正确层级保证不可变性**：引导状态冻结，AppState 浅合并更新，ToolUseContext 永不存入全局。
- **避免过度响应**：组件只订阅它们读取的那部分状态，防止不必要的重渲染。

**可迁移的设计模式**
1. 在选择 Store 前先对状态分类：不可变引导数据用普通对象，响应式状态用自定义 Store，临时上下文用函数参数。
2. 35 行 Store 对大多数 React 应用已足够，只在需要 DevTools/中间件时才引入 Redux/Zustand。
3. 将临时上下文通过参数传递而非全局存储，防止隐蔽的并发 Bug。

## 第 04 章 System Prompt 工程

> 原文档：[docs/04-System-Prompt-工程.md](../04-System-Prompt-工程.md)

分析 Claude Code 如何构建系统提示，解释 `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` 标记和注入未缓存内容的逃生舱口。

**核心要点**
- **静态/动态边界**：`SYSTEM_PROMPT_DYNAMIC_BOUNDARY` 之前的内容稳定可缓存，之后包含每会话动态数据（工作目录、当前时间、工具列表）。
- **`DANGEROUS_uncachedSystemPromptSection`**：注入必须始终最新内容的逃生舱口，不污染静态前缀的缓存。
- **分层组装**：按定义顺序组合命名片段（`corePersonality`、`toolDescriptions`、`memoryInstructions` 等），各片段可独立测试和替换。
- **工具描述注入**：每个工具通过 `Tool.prompt` 贡献自己的提示片段，工具描述与工具逻辑共同存放。
- **会话级记忆化**：静态片段每会话计算一次并缓存，动态片段每轮重新生成。

**可迁移的设计模式**
1. 用哨兵字符串显式标记缓存边界，并测试静态片段在多轮间永不改变。
2. 将提示组合为有序的命名片段列表，而非单体字符串。
3. 每个工具导出自己的提示文本，变化时自动保持同步。

## 第 05 章 对话循环

> 原文档：[docs/05-对话循环.md](../05-对话循环.md)

深度解析 `query.ts`——驱动每轮对话的核心 AsyncGenerator 状态机，涵盖预处理管道、工具执行循环和 7+ 条错误恢复路径。

**核心要点**
- **AsyncGenerator 架构**：`query()` 是 `async function*`，将 `AssistantMessage` 块 yield 给调用方，UI 在流式传输 Token 的同时，循环内部管理状态。
- **预处理管道**：每条用户消息经过有序转换器（提及展开、文件注入、上下文裁剪）再发送给 API。
- **工具执行循环**：模型返回 `tool_use` 时，执行工具、收集 `tool_result`、追加到对话，再循环回 API，对调用方完全透明。
- **7+ 条恢复路径**：`overloaded_error`、`rate_limit_error`、`context_length_exceeded`、空响应、中断的流等，每种有具体恢复策略。
- **流式/非流式双模式**：SSE 流式响应（默认）和完整 JSON 响应（降级）通过同一生成器接口，隐藏传输差异。
- **轮次元数据追踪**：每轮结束时 yield 指标数据（Token 数、缓存命中、工具调用次数）。

**可迁移的设计模式**
1. 将对话循环建模为 AsyncGenerator，yield 流式传输结果，状态机逻辑内聚于单一函数。
2. 显式枚举并命名每种 API 错误码的恢复路径，不用 catch-all 重试。
3. 传输层与对话逻辑分离，`query.ts` 本身与传输无关。

## 第 06 章 上下文管理

> 原文档：[docs/06-上下文管理.md](../06-上下文管理.md)

解释 Claude Code 如何监控上下文窗口、触发压缩，以及使用熔断器防止无限压缩循环。

**核心要点**
- **Token 预算函数**：一组纯函数计算剩余 Token 数、预警阈值和硬性上限，每次 API 请求前调用。
- **微压缩（Microcompact）**：截断较旧工具结果、折叠重复对，保留近期上下文同时减少约 30% Token。
- **完全压缩（Full Compact）**：将整个对话发送给模型附带"总结"指令，用摘要替换历史，在微压缩不够时触发。
- **熔断器**：追踪连续压缩次数，N 次后仍超限则抛出错误而非无限循环。
- **`FileStateCache`**：以 `{路径, mtime}` 为键的文件内容缓存，重复读取未修改文件跳过磁盘 I/O。
- **渐进式降级**：微压缩 → 完全压缩 → 报错，始终先尝试破坏性最小的选项。

**可迁移的设计模式**
1. 每次 API 调用前检查 Token 预算，主动触发压缩而非等待服务器报错。
2. 任何可递归触发的操作都需要迭代计数器和硬性停止条件（熔断器）。
3. 用 `{路径, mtime}` 作为文件读取缓存键，无需轮询即可正确失效。

## 第 07 章 Prompt Cache

> 原文档：[docs/07-Prompt-Cache.md](../07-Prompt-Cache.md)

详细介绍提示缓存策略——`cache_control` 标记的放置、字节级稳定性强制、子 Agent 的 fork 提示传递和锁存模式。

**核心要点**
- **`cache_control` 放置**：在静态系统提示前缀末尾和对话早期注入的大型稳定消息块末尾插入断点。
- **`CacheSafeParams`**：包装类型，强制要求断点之前的值通过字节级稳定性检查，类型系统编译时拒绝不稳定值。
- **字节级稳定性**：Anthropic 缓存按精确字节序列匹配，Claude Code 用冻结对象和内容寻址键保证稳定性。
- **Fork 提示传递**：子 Agent 继承父 Agent 稳定系统提示前缀的快照，缓存命中延续到子 Agent 的第一次调用。
- **锁存模式**：缓存断点写入消息后，会话期间永不移动或删除。
- **缓存命中指标**：每轮追踪 `cache_read_input_tokens` 和 `cache_creation_input_tokens`，展示在状态栏。

**可迁移的设计模式**
1. 创建 `CacheSafe<T>` 包装类型，只接受已知字节稳定的值，不仅靠运行时断言。
2. 将缓存断点位置视为会话生命周期内的只增承诺，永不移动。
3. 派生子 Agent 时传递父 Agent 稳定前缀快照，让子 Agent 受益于父 Agent 的缓存预热。

## 第 08 章 Thinking 与推理控制

> 原文档：[docs/08-Thinking-与推理控制.md](../08-Thinking-与推理控制.md)

解释 Claude Code 如何通过 `ThinkingConfig` 三种模式、四个努力级别、ultrathink 关键词和 Advisor 服务器工具模式控制模型的扩展思考能力。

**核心要点**
- **`ThinkingConfig` 模式**：`adaptive`（默认，复杂时启用）、`enabled`（始终开启）、`disabled`（始终关闭，用于速度敏感路径）。
- **努力级别**：low/medium/high/max 对应递增的 `budget_tokens`，更高努力给更多思考 Token 但增加延迟和成本。
- **Ultrathink 关键词**：用户输入"ultrathink"时，当前轮升级为 `max` 努力级别。
- **自适应复杂度启发式**：消息长度、代码块存在、工具调用历史等启发式估算任务复杂度，自动选择努力级别。
- **Advisor 服务器工具模式**：对过于昂贵的任务，向更小的模型发起单独调用获取有理据的建议——更廉价的结构化推理。
- **思考 Token 预算隔离**：思考 Token 与对话上下文预算分开计算，防止扩展推理挤占工具结果。

**可迁移的设计模式**
1. 用廉价的启发式规则分类复杂度，只在超过阈值时启用扩展思考。
2. 提供"ultrathink"等关键词让高级用户覆盖默认努力级别，无需修改设置。
3. 完整思考轮次过于昂贵时，用带结构化推理提示的更小模型作为 Advisor 替代。

## 第 09 章 工具系统设计

> 原文档：[docs/09-工具系统设计.md](../09-工具系统设计.md)

描述工具系统架构——30+ 方法的 `Tool` 接口、`buildTool()` 构建器、`tools.ts` 注册表和延迟加载 `ToolSearch` 机制。

**核心要点**
- **`Tool` 接口**：30+ 个方法涵盖完整生命周期：`name`、`description`、`inputSchema`（Zod）、`call()`、`prompt`、`isEnabled()`、`isReadOnly()`、`needsPermission()`、`renderToolUse()`、`renderToolResult()` 等。
- **`buildTool()` 构建器**：填充可选方法合理默认值的工厂函数，将每个工具的样板代码从约 200 行压缩到约 50 行。
- **`tools.ts` 注册表**：导入所有工具、运行 `isEnabled()` 检查并导出活跃工具列表的中心文件。
- **延迟加载 `ToolSearch`**：可选工具 Schema 列在清单中，直到调用 `ToolSearch` 时才加载，减少启动内存和系统提示大小。
- **Zod 输入 Schema**：一式三份——API 的 JSON Schema、运行时验证、TypeScript 类型推断。
- **工具 UI 协议**：`renderToolUse()` 和 `renderToolResult()` 生成终端 UI 节点，渲染逻辑与工具逻辑共同存放。

**可迁移的设计模式**
1. 预先设计包含渲染、权限和提示贡献的丰富工具接口，防止日后临时添加造成不一致。
2. 带合理默认值的 `buildTool()` 工厂确保新工具开箱即用，无需复制样板代码。
3. 在清单中注册工具元数据，仅在实际请求时加载实现，保持常见路径精简。

## 第 10 章 BashTool 深度剖析

> 原文档：[docs/10-BashTool-深度剖析.md](../10-BashTool-深度剖析.md)

深度分析 BashTool（约 12,400 行 / 18 个文件）——tree-sitter AST 安全分析、多阶段权限链和可选的 macOS 沙箱。

**核心要点**
- **规模**：18 个文件约 12,400 行，代码库中体量最大的单一模块，复杂性反映了执行任意 Shell 命令的安全敏感性。
- **Tree-sitter AST 分析**：将 Shell 命令解析为 AST，精确检测命令注入、管道链、子 Shell 转义以及 `rm -rf /` 等危险模式，而非正则匹配。
- **多阶段权限链**：静态允许/拒绝列表 → AST 安全分析 → 每工具权限规则 → 全局权限模式检查 → 可选用户确认提示。
- **沙箱（仅 macOS）**：`sandbox-exec` 配置文件限制文件系统写入、网络访问和进程派生，根据工具声明能力动态生成。
- **持久 Shell 会话**：长期存活的 Shell 进程支持有状态工作流（`cd` 持久化、环境变量延续），同时追踪 cwd 变化。
- **输出捕获与截断**：stdout/stderr 有大小限制，超大输出截断附加摘要，防止上下文窗口溢出。

**可迁移的设计模式**
1. 用 AST 而非正则做安全分析，正则可被绕过且对合法代码产生误报。
2. 从最廉价到最昂贵地分层权限：静态列表 → 程序化规则 → AI 分类 → 用户确认。
3. 维护持久子进程，追踪 cwd 和环境变化，比每次派生新进程更强大。

## 第 11 章 命令系统

> 原文档：[docs/11-命令系统.md](../11-命令系统.md)

梳理斜杠命令系统架构——`Command` 联合类型、`commands.ts` 聚合 70+ 个内置命令以及 Skills、Plugins 和 Workflows 的分发逻辑。

**核心要点**

## 第 12 章 Agent 系统

> 原文档：[docs/12-Agent-系统.md](../12-Agent-系统.md)

解释 `AgentDefinition` 类型层次、`runAgent()` 生命周期和 `createSubagentContext()` 隔离机制，使 Agent 在会话中作为独立子进程运行。

**核心要点**
- **`AgentDefinition` 类型**：`built-in`（TypeScript 定义）、`custom`（前置元数据 Markdown）、`plugin`（插件贡献），共享公共调用接口。
- **`runAgent()` 生命周期**：接受定义和任务，创建隔离上下文，运行对话循环，返回结构化结果或流式传回父 Agent。
- **`createSubagentContext()` 隔离**：独立的对话历史、工具子集、权限范围和工作目录快照，防止子 Agent 污染父 Agent 状态。
- **工具子集**：Agent 定义中声明 `tools` 白名单，`runAgent()` 过滤全局注册表，限制能力在所需范围内。
- **权限继承与覆盖**：默认继承父 Agent 权限模式，可声明更严格模式（如 `read-only`）强制最小权限。
- **Agent 间通信**：结果以结构化 `AgentResult` 对象返回，父 Agent 将输出作为工具结果接收。

**可迁移的设计模式**
1. 为每次子 Agent 调用创建新上下文对象，永不在父子之间共享可变状态。
2. 在 Agent 配置中白名单工具，而非暴露完整工具注册表，强制最小权限。
3. 将 Agent 输出设计为带类型的 `AgentResult`，使调用代码能以编程方式处理成功/失败/部分结果。

## 第 19 章 Feature Flag 与编译期优化

> 原文档：[docs/19-Feature-Flag与编译期优化.md](../19-Feature-Flag与编译期优化.md)

介绍双层特性开关系统——编译期 DCE 与运行时 A/B 测试，以及 `MACRO.*` 构建时常量注入。

**核心要点**
- **`feature()` + `require()` DCE**：常量检查的 `require()` 使 Bun 在编译时消除死分支，移除代码及其传递依赖。
- **`USER_TYPE` `--define`**：构建时注入的常量对构建变体分类（`internal`、`external`、`enterprise`），用于 `feature()` 检查。
- **`MACRO.*` 常量**：`--define` 注入的构建时常量（版本号、构建时间戳、API 端点），访问编译为字面量，运行时零开销。
- **GrowthBook 运行时标志**：渐进式发布和 A/B 测试使用 GrowthBook 从远程服务获取标志状态，按用户属性评估。
- **标志分层**：编译时 `feature()` 作为外层门（代码不存在于构建中），GrowthBook 作为内层门（代码存在但有条件激活）。
- **零成本编译时标志**：`feature()` 使用 `require()`（而非 `import`），禁用路径完全树摇，生产环境无运行时布尔检查。

**可迁移的设计模式**
1. 用常量门控的 `require()` 替代动态 `import()` 包裹可选特性，实现零成本 DCE。
2. 按构建变体的能力集用编译时标志，渐进式发布和实验用运行时标志，不要混用。
3. 通过 `--define` 常量注入构建元数据（版本、时间戳、环境），而非运行时读取环境变量。

## 第 20 章 API 调用与错误恢复

> 原文档：[docs/20-API调用与错误恢复.md](../20-API调用与错误恢复.md)

记录 `withRetry` AsyncGenerator 包装器、529/429 差异化处理、流式/非流式双模式和多提供商降级链。

**核心要点**
- **`withRetry` AsyncGenerator**：用重试逻辑包装 API 调用生成器，指数退避重新调用，透明 yield 已传输 Token 维持流连续性。
- **529 vs. 429 处理**：529（服务器过载）用激进短间隔重试（1～4 秒）；429（限速）用 `Retry-After` 响应头值或更长退避。
- **流式/非流式双模式**：SSE 流式响应和完整 JSON 响应通过同一生成器接口，薄适配器标准化为 AsyncIterable。
- **多提供商支持**：抽象 Anthropic 直连、AWS Bedrock 和 Google Vertex AI，提供商选择由配置驱动。
- **退避时加入抖动**：±20% 随机抖动防止多实例同时退避的雷群效应。
- **不可重试错误直接透传**：401、400 和内容策略违规不重试，直接传递原始错误码。

**可迁移的设计模式**
1. 在包装生成器中实现重试，重新调用内部生成器，保持重试逻辑外置并优雅处理部分流恢复。
2. 区分 429 和 529 的重试策略，使用相同策略会浪费时间或烧光配额。
3. 将提供商差异抽象在各提供商适配器类中，保持对话循环与提供商无关。

- **CLAUDE.md**：项目级指令，提交到代码库，会话开始时注入静态系统提示前缀，是团队共享项目知识的主要机制。
- **自动记忆（memdir）**：`~/.claude/memory/` 中的简短 Markdown 文件，模型学到值得跨会话记住的内容时自动创建更新。
- **会话记忆**：仅在当前对话中存活的临时内存映射，用于会话内回忆，无需持久化到磁盘。
- **Agent 记忆**：每个 Agent 独立的记忆存储，支持多 Agent 工作流而不交叉污染。
- **相关记忆注入**：每轮对话前，根据与当前查询的相关性（嵌入相似度或关键词匹配）评分，注入排名前 k 的记忆。
- **记忆文件格式**：带可选 YAML 前置元数据的纯 Markdown，无需特殊编码。

**可迁移的设计模式**
1. 将项目记忆（CLAUDE.md，Git 共享）与个人记忆（memdir，用户私有）分离，永不混合内容。
2. 根据相关性评分只注入排名前 k 的记忆，保持上下文占用低同时呈现最有用的记忆。
3. 将记忆存储为纯 Markdown 文件，人类可读、可编辑、可版本控制，无需特殊工具。

## 第 24 章 Skill/Plugin 开发实战

> 原文档：[docs/24-Skill-Plugin开发实战.md](../24-Skill-Plugin开发实战.md)

扩展 Claude Code 的四个扩展点实践指南——Hooks、Skills、Agents 和 Plugins。

**核心要点**
- **四层扩展层次**：Hook（Shell 脚本响应事件）→ Skill（Markdown 添加斜杠命令）→ Agent（前置元数据 Markdown 添加子 Agent）→ Plugin（完整包添加命令+Agent+工具），每层能力递增，复杂度也递增。
- **SKILL.md 格式**：带 YAML 前置元数据（命令名）和自然语言提示体的 Markdown 文件，放置在 `.claude/skills/` 或 `~/.claude/skills/`，无需编译。
- **Agent 前置元数据**：带 YAML 前置元数据（`name`、`description`、`tools`、`model`、可选 `system_prompt`）的 Markdown 文件，正文成为系统提示，放置在 `.claude/agents/`。
- **Plugin 结构**：`~/.claude/plugins/<插件名>/` 目录，含可选 `package.json`、`skills/`、`agents/` 和 `hooks/` 子目录。
- **通过 MCP 扩展工具**：需要添加新工具的插件在 `package.json` 中注册 MCP 服务器，通过 MCP `tools/list` 协议发现工具。
- **本地测试**：Skills 和 Agents 热重载，Plugins 需要一次性 `claude plugin install <路径>` 步骤。

**可迁移的设计模式**
1. 按复杂度分层扩展 API：文件快速入门 → 结构化中间层 → 完整程序化层，用户可逐步获得更多能力。
2. 前置元数据存结构化配置，Markdown 正文存自由形式提示，将机器可读配置与人类可读指令分离。
3. 以 MCP 作为工具扩展边界，获得与更广泛 MCP 生态系统的互操作性。

## 第 25 章 架构模式总结

> 原文档：[docs/25-架构模式总结.md](../25-架构模式总结.md)

将全书 25 章综合提炼为七个可迁移的架构模式，每个模式都配有具体的实现方案。

**七个核心模式**

1. **编译期 DCE via `feature()` + `require()`**：用常量检查的 `require()` 门控可选特性，让打包器在构建时消除死代码，实现零运行时开销的构建变体。

2. **分层启动与快速路径**：将初始化结构化为层级（引导 → CLI 解析 → 可选 UI → 完整会话），在满足请求的最早层返回，永不加载不需要的内容。

3. **基于 `useSyncExternalStore` 的最小响应式 Store**：35 行自定义 Store 满足 React 18 的无撕裂渲染协议，只在需要 DevTools/中间件时才引入 Redux/Zustand。

4. **`onChange` 副作用驱动的派生状态**：通过 `onChange` 订阅响应状态变化，而非内联计算派生状态，支持异步副作用并解耦触发与效果。

5. **子 Agent 上下文隔离**：每次子 Agent 调用获得全新上下文对象（对话历史、工具子集、权限），父子之间共享可变状态会导致隐蔽且难以复现的 Bug。

6. **延迟工具加载**：在清单中发布工具元数据，仅在首次调用时加载实现，使启动内存和系统提示大小与实际使用量成正比。

7. **AI 操作的纵深防御**：对任何有副作用的操作分层使用静态规则 → 程序化分析 → AI 分类 → 用户确认，永不依赖单一关卡，最廉价的关卡放在最前面。

**元模式**
- 在正确层级应用模式，抵制在预期层级之外应用的冲动。
- 优先使用经过验证的语言和平台原语（`useSyncExternalStore`、`AsyncGenerator`、`require()`），而非框架特定抽象。
- 安全是分层系统而非检查清单，每层都假设前一层可能失效。
